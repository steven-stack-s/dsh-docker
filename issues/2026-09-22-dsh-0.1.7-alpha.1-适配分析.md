## 一、结论速览

| 判定 | 结论 |
|---|---|
| 部署机制是否需要改 | **不需要**。seed → 挂载卷复制 → 启动链路未变；`ver_gt` 会正确判定 `0.1.7-alpha.1 > 0.1.6-alpha.2`，卷内升级**不会被 seed 顶回去** |
| 是否有破坏性变更 | **有，但这次不是"静默机制失效"型**（对比 0.1.6-alpha.2 的 `patchReload` 翻车）。本次是**数据格式换代（Session V3 → V4）+ 设置存储换代（settings.yaml → profile 插件配置）** |
| 最大风险 | **会话数据单向迁移**：/data/dsh/sessions 现为 `session.v3.jsonl.zstd`（122 MB / 4 个 workspace 目录）。升级后读取会转 V4、继续对话会**发布 V4 新格式文件**，旧版本 dsh 将无法再读这些会话 → **升级前必须备份 sessions 与 storages** |
| 会不会起不来 | **单点不会**。profile bundles 里的 `dsh-experimental-agent-team-web-profile` 已被上游删除，但实测新版是**跳过 + 明确警告 + 继续启动**（exit 0），不再是致命错误 |
| HMR 加固是否还成立 | **成立**。`dsh-base/cordis.patch.yml` 的 `hmr` 条目两版逐字节相同，`--patch` 注入 `hmr-off.yml` 的做法继续有效 |
| 本机破坏性配置 | **无**。settings.yaml 未使用被移除的 `protocol` 字段；无自定义 agent 预设目录；profile patch 按 id（remote/better-sidebar/compaction-basic）覆盖，未引用被改名/删除的条目 |
| 需要动手改的地方 | **2 处必改**（备份 + 清理已删除 bundle 行），**3 处建议改**（第三方插件核对、settings 抽查、文档版本号） |

## 三、对本地部署的风险清单（分级）

### P0 —— 会话数据单向迁移（唯一"不可逆"项）

**现状（实测）**：`/data/dsh/sessions` 122 MB，四个工作区目录，文件名为 **`session.v3.jsonl.zstd`**（另有更早的无版本后缀文件）。

**新版行为**：`dsh-session` 的 `SESSION_FORMAT_VERSION` 推进到 V4，新增 `dsh-session-format-v3-to-v4` 库负责转换。该库自述为
*"Restore supported released V3 Sessions as V4 **without rewriting their stored generation**"* —— 即**读取时转换到 V4 内存表示**，但 `write-open` 路径"publishes only the current-format successor"，**一旦打开旧会话并继续写入，就会落盘 V4 新文件**。

**后果**：升级后产生的新格式会话，**回退到 0.1.6-alpha.2 时不可读** —— 与 docs 03 里已有的同类警告（0.1.2→0.1.5 的 V3 迁移）完全同型。

**必做**：升级前备份

```bash
docker exec dsh sh -c 'tar czf /data/dsh/backup-sessions-$(date +%F).tgz -C /data/dsh sessions storages'
# 或宿主机侧对 /data/dsh 卷做快照
```

回滚 = **dsh 版本 + sessions/storages 数据一起回滚**，只降版本不还数据会出现"会话列表空白 / 无法打开"。

### P1-a —— profile bundles 引用了已被删除的包（不会崩，但必须清理）

本机 `/data/dsh/profiles/web/package.json` 的 `dsh.profile.bundles` 含：

```
"@deepseek-ai/dsh-experimental-agent-team-web-profile"   ← 0.1.7 已删除（npm 最新版停在 0.1.6-alpha.2）
"@deepseek-ai/dsh-experimental-agent-team-profile"       ← 仍存在（0.1.7-alpha.1）
```

**实测（新版 + 含该 bundle 的探针 profile）**：

```
$ DSH_HOME=<probe> dsh@0.1.7-alpha.1 --profile probe-with-webprofile --dump-config
dsh: skipping profile bundle "@deepseek-ai/dsh-experimental-agent-team-web-profile":
  Error: dsh: cannot resolve profile bundle "..." from the dsh installation or <profile>;
  run 'dsh plugin --profile ... install' if its dependency is not installed
exit=0        # 其余 4 个 section 正常合成（旧版为 5 个）
```

→ **不会导致启动失败**（这正是 release notes 里"无法读取的可选插件包不再直接中止 Profile 加载"的落地），但会：
1. 每次启动打一条 skip 警告，污染 `last-web-boot.log` 与 `rescue doctor` 判读；
2. 该 bundle 原本注入的行消失（本机场景下其 UI 能力已由 `dsh-experimental-agent-team-profile` → `dsh-experimental-client-ui-agent-team` 覆盖）。

**建议**：升级前从 bundles 数组删掉这一行（**只删这一行**，保留 team-profile）。注意 entrypoint 只在 manifest **不存在**时预置 bundles，不会覆盖本机已有清单，所以必须手工改。

### P1-b —— profile 的 cordis/schemastery 与安装树出现版本分叉

安装树将用 **cordis 4.0.3 / schemastery 3.18.3**，而 `/data/dsh/profiles/web/pnpm-lock.yaml` 锁的是 **cordis 4.0.2 / schemastery 3.18.2**（12 个第三方插件的 peer 记录都挂在 4.0.2 上）。

DSH 的 profile-resolution 本来就会把 installation scope 的包路由给 profile 插件（避免重复实例），但**peer 版本不一致 + 加载器（cordis-plugin-loader 1.0.3→1.0.4、include 1.0.7→1.0.8）升级**是否引发"双 cordis 实例 / 服务注册不共享 / 插件不激活"，**本次未在本机复现验证**（探针 profile 未装第三方插件）。

**验证手段（升级预演时必做）**：
```bash
docker exec dsh dsh --profile web --dump-config | grep -n "cordis\|loader" | head
docker exec dsh dsh --profile web --dump-config > /tmp/after.txt   # 与升级前对比 entry 数与 skip 警告
docker logs dsh 2>&1 | grep -i "did not activate"                  # 期望：无输出
```

### P1-c —— settings.yaml 一次性导入（本机映射已核对）

0.1.7 会把 `$DSH_HOME/settings.yaml` 的各 section **导入一次**到同 id 的插件条目，随后重命名为 `settings.yaml.imported`。本机 settings.yaml 的 7 个 section 与新版本组合（探针 profile 177 个 entry id）逐一比对：

| section | 结果 |
|---|---|
| `agent-default-model` | MATCH ✅（新版仍接受 `provider: deepseek-official` / `model: deepseek-flash`） |
| `ui-chat`、`locale`、`llm-pi-ai` | MATCH ✅ |
| `ui-onboarding` | 无同名 id，但新版文档规定别名为 `ui-settings-general` ✅ |
| `dsh-better-sidebar`、`trae` | 探针 profile 未装这两个第三方插件（本机已装）→ 升级后应 MATCH；**需在预演中复核** |

**风险**：一次性导入是"单次机会"。若某 section 因插件未激活 / id 不匹配被组合拒绝，它**只留在 `settings.yaml.imported` 里、不再生效**（表现为设置悄悄回默认值，例如默认模型、Trae 上下文预算 `DeepSeek-V4-Flash-Official: 1000000`）。

**建议**：升级前单独备份 `settings.yaml`；升级后立刻核对 Trae 的 `contextBudgets` 与默认模型是否仍在（Web 设置页或 `--dump-config`）。

### P1-d —— 第三方插件适配面（需逐个核对，本次未改代码）

| 变更 | 涉及的本地插件 | 核对点 |
|---|---|---|
| workspace files 统一 `readBytes` | `@xgone/dsh-remote`、`dsh-free-search` 等 | 是否调用旧 `workspaceFiles.read` 语义 |
| 自定义事件中的附件不再自动读取/导出 | **`@steven-stack-s/dsh-memos-local`** | `adapters/deepseek-harness/bridge.ts` 的 `onSessionEvent` 分支与 `session.header`（V4 事件/头部字段） |
| 设置存储换代 | `dsh-free-search`、`dsh-cost-meter`、`dsh-workbuddy-connect`、`dshmarket`、`dsh-better-sidebar` | 声明了自己的设置 id 才能接住导入 |
| 客户端 bundle 契约 | memos 的 `client/client.js`（`__ModuleLoader__.load`） | 实测 `dsh-client-ui-slots` **零改动**、`dsh-client-modules` 2 文件改动 —— 风险低但需回归一次 UI |

### P2 —— 低风险项（已核对，无需动作）

- **HMR 加固仍有效**：两版 `dsh-base/cordis.patch.yml` 的 `hmr` 条目（`name: '@deepseek-ai/dsh-hmr'`、`disabled: !!js "!ctx.get('profileContext')"`）逐字节一致 → `--patch hmr-off.yml` 继续生效。
- **seed 只升不降**：`vercmp.sh` 的 `ver_gt` 正确处理预发布段，`0.1.7-alpha.1 > 0.1.6-alpha.2` 为真 → 镜像 seed 不会覆盖卷内的新版；反过来，回滚到 **= seed 的 0.1.6-alpha.2** 也不会被覆盖。
- **本地 patch 层未踩改名**：`/data/dsh/profiles/web/cordis.patch.yml` 只按 id 覆盖 `remote` / `better-sidebar` / `compaction-basic`；`settings-file → settings` 的改名不涉及这些 id，且 `compaction-basic` 的 `summarizationProvider/Model` 键在新版 schema 中**仍然存在**（实测源码）。
- **`--dump-config` 与 patch 语义**：新版新增 `--dump-config-schema`，原 `--dump-config` 行为不变（探针 profile exit 0）。
- **无自定义 agent 预设目录**（`/data/dsh` 下无 presets），预设机制更替无影响。

## 四、建议的升级路径（保守版）

```bash
# 0) 备份（必须）
docker exec dsh sh -c 'tar czf /data/dsh/backup-pre017-$(date +%F-%H%M).tgz -C /data/dsh \
  sessions storages settings.yaml profiles/web/package.json profiles/web/cordis.patch.yml'

# 1) 清理已删除的 bundle（只删一行）
#    编辑 /data/dsh/profiles/web/package.json → dsh.profile.bundles
#    移除 "@deepseek-ai/dsh-experimental-agent-team-web-profile"

# 2) 预演（不换镜像、可秒级回退）：装到容器内并只做只读检查
docker exec dsh npm install -g @deepseek-ai/dsh@0.1.7-alpha.1
docker exec dsh dsh --version
docker exec dsh dsh --profile web --dump-config > /tmp/dump-after.txt   # 与升级前对比
docker restart dsh
docker logs dsh 2>&1 | grep -E "dsh version|did not activate|skipping profile bundle"
docker inspect -f '{{.State.Health.Status}}' dsh

# 3) 功能回归（重点看：默认模型、Trae 上下文预算、memos 面板、侧边栏/设置页）

# 4) 回退（如需）：数据一起回滚
docker exec dsh npm install -g @deepseek-ai/dsh@0.1.6-alpha.2
docker exec dsh sh -c 'tar xzf /data/dsh/backup-pre017-*.tgz -C /data/dsh'
docker restart dsh
```

> 顺序提醒（沿用 docs 03）：**先升镜像、再升 dsh**。若要长期停在 0.1.7-alpha.1，应重建镜像并把 `ARG DSH_VERSION=0.1.7-alpha.1`、`DSH_IMAGE` tag 一起推进，否则"卷内新版 + 镜像旧 seed"在下次**重建镜像/换 tag** 时会被重新对齐。

## 十、收尾：四处插件兼容修复 + 升级完成（17:00–18:40）

### 10.1 第三个断裂：Session V4 拒收 `source.kind === "plugin"`（每轮对话都失败）

用户在 web 里发消息后，会话区显示：

```
本轮运行失败  format v4 message requires a producer-owned source kind
```

**根因**（`dsh-session-format-v3-to-v4/lib/index.js:126`）：V4 校验要求 `source.kind` 是非空字符串，
且**不得等于 `"plugin"`**（注释原话 *refuses retired plugin wrappers*）。而 memos 注入记忆召回
上下文时仍在用旧包壳：

```js
// dist/adapters/deepseek-harness/index.js（每轮 agent/pre-step 都走）
source: { kind: "plugin", plugin: DEEPSEEK_HARNESS_PLUGIN, form: "recall" }
// dist/adapters/deepseek-harness/host-llm.js
source: { kind: "plugin", plugin: HOST_LLM_MESSAGE_SOURCE }
```

官方 `producerKind()` 对未登记生产者解析出的新形状是 `plugin:<name>`，且**删除 `plugin` 字段**；
`form: "recall"` 仍在 0.1.7 的 `ContextForm` 词汇表内（*Material lifted out of another session log*）。

**修复**：
- 运行时：`/data/dsh/memos-v4-source-patch/apply.cjs`（幂等 + 备份 + `node --check`），改 `dist/` 两处；
- 源码（`dsh-memos-local` 仓库）：`adapters/deepseek-harness/index.ts` 与 `host-llm.ts` 改为
  `` `plugin:${...}` ``，随下次发版（建议 `2.0.20-dsh.2`）生效。

同类残留：`dsh-better-sidebar/lib/index.js` 也构造 `kind: "plugin"`，但它被 profile patch 层的
`disabled: true` 挡住，暂不发作。

### 10.2 第四个断裂：图标契约改名 → 「插件市场」整页 React #130（用户侧修复）

**症状**：0.1.7 之后打开「设置 → 插件市场」抛 `Minified React error #130`
（*Element type is invalid … got: undefined*）—— 崩掉的是**整个 Web 应用根**，不只是市场页。

**根因**：0.1.7 把 `@deepseek-ai/dsh-client-ui-primitives` 的图标契约从**尺寸后缀**改成**笔画后缀**：

```
Icon<Stem>14 / Icon<Stem>16   ->   Icon<Stem>Regular / Icon<Stem>Medium
```

实测当前宿主的 **265 个导出里没有任何** `Icon*14` / `Icon*16` 形式的名字，而若干第三方 client bundle
仍按旧名做**命名空间成员访问**：

```js
react_jsx_runtime.jsx(_deepseek_ai_dsh_client_ui_primitives.IconSparkle16, ...)
```

宿主 `client-modules` 的 `require` 对「已注册模块的缺失成员」**不抛错、只返回 `undefined`**
→ `jsx(undefined)` → React #130。

**诊断时的关键排除**：这不是「模块整个缺失」—— 那会抛
`client-modules: require(...) missed the module table`（页面显示加载失败横幅），与观察到的 #130 不符；
说明模块可用，只是缺这些成员。

**修复**（`/data/dsh/dshmarket-icon-compat-patch/`：纯改名、不动逻辑，幂等 + 备份 + `--check`）：

| 目标 | 规模 |
|---|---|
| `dshmarket/client/client.js` | 17 名 / 66 处（市场页本身） |
| `dsh-connect-trae/lib/client.js` | 1 名 / 1 处 |
| `dsh-better-sidebar/lib/client.js` | 28 名（当前被 `disabled: true` 挡住，预防性） |

映射规则 `Icon<Stem><14|16>` → `Icon<Stem>Regular`，且**新名一律先对照当前宿主导出表核验**，
核验不过就拒绝写入 —— 绝不把 `undefined` 换成另一个 `undefined`。配套 `scan.cjs`（扫描受影响处）
与 `verify.cjs`（核验导出名）。像 `@xgone/dsh-remote` 那样已用 `?? null` 降级的不在改动范围内。
