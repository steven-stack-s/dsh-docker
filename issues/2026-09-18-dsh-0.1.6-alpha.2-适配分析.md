## 二、0.1.6-alpha.2 真实变更（实测确认）

### 2.1 HMR 整体换代（本次最重要的变更）

| 维度 | 0.1.6-alpha.1 | 0.1.6-alpha.2 |
|---|---|---|
| 实现包 | `@deepseek-ai/cordis-plugin-hmr`（外部插件） | **`@deepseek-ai/dsh-hmr`**（新包，2026-09-17 首发，仅此一版） |
| 开关位置 | profile manifest 的 `patchReload` 字段 | base 组合包的 `hmr` 条目 |
| 默认态 | `disabled: true`（模块热重载 opt-in） | `disabled: !!js "!ctx.get('profileContext')"` → **由启动器拉起即启用** |
| 新建 profile manifest | 含 `patchReload` | **不含** |
| dsh-app-boot 中的 `patchReload` | 被读取 | **引用被完全删除** |

实测两版 `dsh-base/cordis.patch.yml` 中 `hmr` 条目的差异：

- alpha.1：`name: '@deepseek-ai/cordis-plugin-hmr'`、`disabled: true`、`config.root: ['.']`，
  且注释明说「Module reload is opt-in per profile；`patchReload: live` 的配置监听走
  launcher 的 watch-only fallback，不需要这一行」。
- alpha.2：`name: '@deepseek-ai/dsh-hmr'`、`disabled: !!js "!ctx.get('profileContext')"`、
  `config.root: []`，注释改为「Profile configuration reloads by default; module roots are opt-in」。

即**配置热重载从「opt-in」翻转成「默认开」**。

### 2.2 其它新增/变化

| 变更 | 说明 |
|---|---|
| `@deepseek-ai/dsh-plugin-manager` | 新增依赖；与 `dsh plugin` 共享包操作与 profile 写锁 |
| `@deepseek-ai/dsh-atomic-write` | 新增依赖（原子写） |
| `exports` 字段 | 新增 `./profile-boot` 契约（供 Desktop host 复用 profile 生命周期） |
| `dsh <name>` | 新增简写；`--profile <name>` 仍兼容（本项目启动命令无需改） |
| agent-team profile | `dsh-experimental-agent-team-profile` / `-web-profile` 由 devDeps 提为 deps |

> 注：`node-addon-require-builtin` 的版本约束两版相同（`^0.1.6`），未变。

## 三、对 dsh-docker 的影响

### P0 —— 关闭 HMR 的手段已失效（真问题，本次已修）

`scripts/entrypoint.sh` 第 ⑤ 步原先做两件事：预置带 `patchReload: "startup"` 的 web
manifest，以及把既有的 `"live"` 用 sed 改写成 `"startup"`。在 alpha.2 下**这两件事都不再
影响 HMR** —— 字段已无人读取，写它等于写进空气。

后果链：

1. web profile 的配置热重载**默认开启**（与 README/docs 的承诺相反）；
2. read_only 根 FS 下 `ctx.loader.internal` 可能缺席，此时 `dsh-hmr` 会抛
   `Error: --expose-internals is required for HMR service`（源码 `dsh-hmr/lib/index.js:317`），
   使 dsh 启动即崩。**真机实测修正**：在当前的默认加固组合下（`NARB_DISABLE_NATIVE_CACHE=1`
   + `tmpfs /tmp:exec` 已让该原生绑定可用）**并未崩溃** —— 新旧两种做法都能起来（见 §五 5.3）。
   故本条的实际危害收敛为「**行为与文档承诺不符**」+「read_only 加固失效」，而不是「容器起不来」；
   但一旦该绑定再次不可用（例如把 /tmp 改回 noexec），崩溃这条路径就会重新成立 ——
   这正是仍要显式关掉 HMR、而不是听任其默认启用的理由；
3. `test-nonroot.sh` 只 grep entrypoint 里的那两行文本，**因此照样全绿** ——
   典型的「门禁盯实现、不盯保障」，保护蒸发了却没有任何信号。

**实测（隔离安装 alpha.2）**：`--dump-config` 中 hmr 条目的最终值 ——

| 场景 | hmr 条目最终值 |
|---|---|
| 不带修复（等价于旧 entrypoint 的效果） | `disabled: !!js '!ctx.get(''profileContext'')'` → **启用** |
| 带修复（启动时注入 `--patch`） | `disabled: true` → **关闭** |

### P1 —— 存量 profile 的 `patchReload` 字段（实测无害）

从 alpha.1 升上来的部署，其 web manifest 里仍留着 `"patchReload": "startup"`。实测：
alpha.2 **静默忽略**该字段，`--dump-config` 退出码 0、无告警，真实启动 25s 稳定。
故**不做**字段删除 —— sed 摘 JSON 字段极易留下尾逗号而毁掉 manifest，收益为零。

### P2 —— 文档与示例版本号

- dist-tag 对照表已过时：实测 2026-09-18 为 `latest → 0.1.5-rc.2`（原写 rc.1）、
  `next → 0.1.5-rc.2`、`alpha → 0.1.6-alpha.2`；
- README 中英的 HMR 加固说明、docs 07 中英的「安全加固」节、compose/workflow 的示例 tag、
  README 的 DSH 版本徽章，均已同步。

### 为什么用启动参数而不是继续写 manifest

`--patch` 是 launcher 的叠加层，应用在 profile 层之后，实测足以把 `disabled` 覆盖为 true；
且它在 **`0.1.5-rc.2` / `0.1.6-alpha.1` / `0.1.6-alpha.2` 上均存在**（逐一解包确认），
所以容器内 `docker exec npm install -g` 升级或回退 dsh 都不会让它失效。相比之下「往 manifest
写字段」是**版本相关**的 —— 字段会随版本被删除，这正是本次翻车的根因。另外它不触碰用户的
`cordis.patch.yml`，也不与用户自己的 patch 层冲突。

## 五、验证证据

### 5.1 单测门禁

`scripts/t/test-*.sh` **27/27 全绿**（含新增的 `test-hmr-off.sh`）。

新门禁刻意**盯保障而非实现文本**：

- 叠加层内容真的禁用了 `hmr`（在 `id: hmr` 条目内断言 `disabled: true`）；
- 镜像真的携带它（Dockerfile 的 COPY + CRLF 归一两处都断言）；
- **每条** `dsh` 启动路径都注入了它 —— 用**数量断言**（`grep -c 'dsh --profile'` 的条数与含
  `HMR_OFF_PATCH` 的条数相等），将来新增启动路径若忘记注入会自动红灯；
- 反向断言：不得退回已被 alpha.2 删除的 `patchReload` 机制。

门禁自身有效性用 3 个负向用例验证（均如期变红）：

| 负向场景 | 结果 |
|---|---|
| 撤掉 supervise 里一处的 `$HMR_OFF_PATCH` | `FAIL-supervise-launch-without-hmr-off(2/3)` |
| 把叠加层的 `disabled: true` 改成 `false` | `FAIL-hmr-off-does-not-disable` |
| 让 lifeboat 模板重新带上 `patchReload` | `FAIL-lifeboat-template-carries-removed-patchreload` |

### 5.3 真机验证（192.168.1.88，特权 DinD，真 Docker）

在隔离沙箱上构建了含本次全部改动的镜像（`dsh-alpha2:fixed`）并跑真容器：

| 验证项 | 结果 |
|---|---|
| CI 门禁 3 等价：镜像内 seed 版本自证 | `docker run --entrypoint /opt/dsh-seed/bin/dsh <img> --version` → `0.1.6-alpha.2` |
| 镜像内叠加层内容 | `/opt/dsh-rescue/hmr-off.yml` 含 `- id: hmr` / `disabled: true` |
| **救援资产可读性（以 uid 1000）** | **第一次构建：Permission denied**（见下方专节）；修复后 `READ-OK` |
| **`read_only` + 完整加固启动** | `--read-only` + `tmpfs /tmp:size=128m,exec` + `cap_drop:[ALL]` + 4 个 `cap_add` + `no-new-privileges` → **10s healthy**；日志 `HMR disabled via launch overlay: /opt/dsh-rescue/hmr-off.yml`，无 `expose-internals` 错误 |
| **反证：改用改动前的 entrypoint**（不注入 `--patch`），同一加固配置 | 同样 healthy，但日志只有它自己那句 `patchReload -> startup (HMR off, read-only safe)` 的**自我声明** —— 而 alpha.2 已忽略该字段，**HMR 实际并未被关闭** |
| `scripts/t/e2e-container-selftest.sh` | **六项全 PASS**：首启 healthy / rescue snapshot / 改坏依赖后自动回滚并恢复 / rescue verify / selfheal status / rescue export |

#### 真机抓到的缺陷：救援资产权限依赖构建机 umask（本地测不出）

第一次真机构建出的镜像里，`/opt/dsh-rescue/hmr-off.yml` 是 **`0600 root`**：以 uid 1000 运行
`cat` 直接 `Permission denied`，entrypoint 注入的 `--patch` 会被拒，**关闭 HMR 的加固完全失效** ——
而本地 27/27 单测全绿。根因是 `COPY` 保留源文件权限，源权限取决于**构建机的 umask**：
git 只记录 644/755，正常 umask（022）下 checkout 出来恰好可读，只在 umask 收紧（如 077）的
构建机上落成 0600 —— 一条隐式的构建环境依赖。

影响面不止本次新增的文件：`rescue-supervise.sh` / `diagnose.js` / `report.js` 同样只做了 CRLF
归一而没有 chmod，在 umask 077 下会一并变 0600，使**救援与自愈**失效。
修复为 Dockerfile 统一 `chmod a+r /opt/dsh-rescue/* /opt/dsh-rescue/lifeboat.tmpl/*`
（+x 仍只给需要执行的那三个），并补两条门禁断言（必须有该 chmod；RUN 续行内不得有注释）。

## 六、剩余不确定项

1. **运行时热重载是否真的未被激活**（观测手段受限）。配置层证据充分（§三 P0 的
   `--dump-config` 对照 + alpha.2 源码 + dsh-hmr README），但真机上没能直接观测到：
   dsh-hmr 重载不打日志，`/proc/*/fd` 里也数不到 inotify 实例（新旧两容器均为 0，无法据此区分）。
   若要更强证据，可在真机上改 `profiles/web/cordis.patch.yml` 后观察行为差异。
2. **`dsh-plugin-manager` 对 `dsh plugin` 的语义影响**。alpha.2 新增该包并与 `dsh plugin`
   共享写锁；rescue 的插件装卸仍走 `dsh plugin --profile ... <pnpm args>`，接口未变，
   但并发语义（写锁）未做真机并发验证。
3. **客户端侧 `dsh-client-hmr`** 出现在 web 组合树中，属前端热更新通道，与容器加固无关，
   未做进一步验证。
