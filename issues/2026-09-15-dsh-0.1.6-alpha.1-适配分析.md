# DSH 0.1.6-alpha.1 变更分析 & dsh-docker 适配清单

> 分析日期：2026-09-15
> 对照基线：`@deepseek-ai/dsh@0.1.5-rc.2`（dsh-docker 当前锁定版） → `0.1.6-alpha.1`（npm dist-tag `alpha`）
> 方法：npm 包解包逐文件 diff + 两版本实机对照实验（真实启动、真实插件失败注入），**不依赖 release notes 转述**

---

## 一、结论速览

| 判定 | 结论 |
|---|---|
| **部署机制是否需要改** | **不需要**。seed → 挂载卷复制 → 启动的完整链路在 0.1.6 下实测通过 |
| **自愈/救援体系是否需要改** | **需要小幅调整**，主要是 CI tag 正则与 healthcheck 语义，见 §4 |
| **是否破坏性** | 对 dsh-docker 而言**基本无破坏**；官方声称的"配置不再自动回滚"**不影响** dsh-docker（它从不依赖该机制） |
| **最大实际风险** | `latest` dist-tag **仍指向 0.1.5-rc.1**，0.1.6 只挂在 `alpha` 下 —— 任何"装 latest"的路径都拿不到 0.1.6 |

## 二、0.1.6-alpha.1 真实变更（实测确认）

### 2.1 包结构变化

**新增依赖：**

| 包 | 说明 |
|---|---|
| `@deepseek-ai/dsh-workflow-ptc` | 工作流编排改在共享沙箱化 PTC 运行时执行 |
| `@deepseek-ai/dsh-mcp-resources` | MCP 资源发现与读取 |

**移除 / 重命名：**

| 变更 | 旧 → 新 |
|---|---|
| 工作流执行器 | `dsh-workflow-worker-thread` → **`dsh-workflow-ptc`**（旧包已不再发布 0.1.6 版本） |
| PTC 运行时（devDep） | `dsh-experimental-code-runtime-python` → **`dsh-experimental-ptc-runtime-python`** |
| 原生 addon | `node-addon-require-builtin` `^0.1.4` → **`^0.1.6`** |

> ⚠️ **必须重建镜像**：Dockerfile 用 `npm install -g @deepseek-ai/dsh@<ver>`，npm 会自动解析新依赖树，无需改 Dockerfile。但**已构建的旧镜像不能靠"容器内 npm install"部分升级**——种子内其它 245 个 `@deepseek-ai/*` 包也一并升到 `^0.1.6-alpha.1`，混装会出问题。

### 2.2 服务名与配置项重命名（影响自定义 patch）

实测 preset 文件 diff（`dsh-base` / `dsh-web-app` / `ptc` 三套 preset）：

```diff
-    - id: workflow-worker-thread
-      name: '@deepseek-ai/dsh-workflow-worker-thread'
+    - id: workflow-ptc
+      name: '@deepseek-ai/dsh-workflow-ptc'
+      disabled: true          # 默认关闭
```

并在 ptc preset 中：
```diff
-# The row waits for the host's `codeRuntime`
+# The row waits for the host's `ptcRuntime`
```

- **服务名 `codeRuntime` → `ptcRuntime`**：任何自定义插件若 `inject: ['codeRuntime']` 会激活失败。
- **Ralph 默认关闭**：`tool-ralph` 与 `workflow-ptc` 行均标 `disabled: true`（与官方 release note 一致）。

> 📌 **重要纠正**：社区流传的"`code` preset 改名 `ptc`"实际发生在 **0.1.5**，不是 0.1.6。
> 实测两版 preset 目录均为 `cordis / minimal / ptc / standard`，0.1.5-rc.2 **已经**没有 `code` preset。
> 若仓库/文档中仍写着 preset `code`，那是 0.1.5 之前的问题。

### 2.3 ⭐ 插件启动失败语义变更（本次最重要）

**实测两版源码对照：**

| 版本 | 行为 |
|---|---|
| **0.1.5-rc.2** | 遍历所有条目，**任何一个** `FIBER_FAILED`/`PENDING` → `throw`，整棵树拒绝启动 |
| **0.1.6-alpha.1** | 新增 `requiredStartupEntryIds` 白名单；**只有白名单内的条目**失败才 `throw`，其余仅 `warn` 并继续运行 |

0.1.6 新增的必需条目白名单（源码 `dsh-app-boot`）：

```js
const requiredStartupEntryIds = new Set([
  "agent-loop", "webserver", "modules",
  "connection", "headless-runner", "acp", "sdk-jsonrpc-server"
]);
```

**实机验证结论（重要，与官方描述有出入）：**

我用真实注入的坏插件做了完整对照实验，实际边界是：

| 失败类型 | 0.1.5 | 0.1.6 |
|---|---|---|
| 包**无法解析**（包不存在） | 启动失败 | **启动失败**（`mountRootInclude` 阶段抛出，白名单救不了） |
| 包能解析但 `apply()` **抛异常** | 启动失败 | **启动失败**（在 include 内，整棵树 reject） |
| 已 settle 树的条目 inactive | 启动失败 | **仅 warn，继续运行** |

> ✅ **对 dsh-docker 的好消息**：dsh-docker 探针的 L4 失败模式 `/did not activate/i` 在 0.1.6 中**仍然存在**（`activationDiagnostic()` 生成 `"N entries did not activate"`），且 0.1.6 新增 `"required startup failure"` 文案。
> **建议**：给 `probe-ready.js` 的 `FAIL_BODY_PATTERNS` 补上 `/required startup failure/i`，覆盖面更全。

### 2.4 新增：插件包解析代（profile resolution generation）

0.1.6 的 CLI 新增了解析模式概念（`profile-boot.js` 的实质变更）：

```js
const resolutionMode = process.pkg !== void 0 ? "runtime"
                     : options.resolutionMode ?? "link";
// link  -> 物化符号链接（默认，等同旧行为）
// dual  -> behavior: "verify"
// runtime -> behavior: "enforce"（pkg 打包场景）
```

新增 `PluginPackages` 服务（`app-boot`）与 `createProfileResolutionGeneration()`。

**实测影响评估：**
- profile 的 `node_modules` **仍会正常物化**（实测：`package.json` 里声明的依赖照样被 symlink 进 `node_modules`），两版一致。
- `.dsh-module-fallback/` 目录 **并非 0.1.6 新增**（0.1.5 已存在），本次实测两版均创建该目录。
- **结论**：这是**向后兼容的增量能力**，dsh-docker 的快照逻辑（抓 `node_modules` + `package.json` / `pnpm-lock.yaml` / `pnpm-workspace.yaml`）**无需改动**。

> 💡 但仍建议：`rescue_snapshot()` 顺手把 `.dsh-module-fallback` 纳入快照范围，属低成本防御（见 §4.3）。

### 2.5 运行时行为（官方 release notes 要点，与容器相关）

| 变更 | 对 dsh-docker 的影响 |
|---|---|
| Node PTC 改**独立进程**执行，`process.env` 为空 | 无（不影响启动/自愈） |
| `run_code` 超时默认 120s / 上限 600s | 无 |
| DeepSeek 默认转 Messages 协议，旧根地址需改 `https://api.deepseek.com/anthropic` | ⚠️ 若用户在 `.env` / profile 里写死了旧 base_url，升级后需改 |
| 图片缓存迁到 `DSH_HOME/cache/attachments/request-images` | 无（在数据卷内，自动创建） |
| 移除 E2B 执行后端 | 无 |
| Linux 子进程终止/清理修复 | ✅ 对容器 PID 1 与僵尸进程回收**有利** |
| MCP 升官方 SDK v2 | 无 |

### 2.6 ⚠️ 关于"取消事务回滚"（官方 note 中的破坏性变更）

官方 release notes 称"移除事务回滚的热更新语义：解析失败保留原配置，插件激活失败可能部分生效"。

**实测结论：这条对 dsh-docker 无影响。** 原因：
1. dsh-docker 的自愈**从不依赖** dsh 内部的配置事务回滚；
2. 它依赖的是**自己的快照 / 回滚体系**（`rescue_snapshot` + `rescue_restore`），操作对象是磁盘上的 `node_modules` + 配置文件，与 dsh 进程内的热更新语义正交；
3. 实测 `cordis-plugin-hmr` 的 `rollback()` 逻辑在 0.1.6 中**依然存在**（模块缓存备份/还原路径未删）。

## 四、需要做的适配（按优先级）

### P0 —— 版本锁定策略（必须处理）

**问题**：`Dockerfile` 的 `ARG DSH_VERSION=latest`，而 npm dist-tags 现状是：

```
latest -> 0.1.5-rc.1     ← 最旧的 rc，不是"最新版"！
next   -> 0.1.5-rc.2
alpha  -> 0.1.6-alpha.1  ← 0.1.6 只在这里
```

#### 为什么 `latest` 是 rc.1 而不是 rc.2

**npm dist-tag 不会自动前进**——它是发布者**手动指定**的别名，不是"最新发布版本"的自动指针。真实时序：

| 版本 | 发布时间 (UTC) | tag | 说明 |
|---|---|---|---|
| 0.1.5-rc.1 | 2026-09-10 03:12 | **`latest`** | 发布时占住 latest |
| 0.1.5-rc.2 | 2026-09-10 14:57 | `next` | **同日下午补丁，只推进到 next，未动 latest** |
| 0.1.6-alpha.1 | 2026-09-15 03:23 | `alpha` | 预览版 |

即：rc.2 是当日热修候选版，官方**有意**没让它顶替 `latest`，保留经过更长时间验证的 rc.1 作为 `npm i` 的默认落地版本。
所以 `latest` 落后于 `next` 是**设计使然，不是遗漏**——`latest` 在这套发布纪律里承担"稳定推荐版"角色。

> ⚠️ 三个 tag 指向**三个不同版本**。`npm install -g @deepseek-ai/dsh@latest` 拿到的是其中**最旧的 rc.1**。

**动作**：
- 发布 tag 用完整版本号（`v0.5.0-dsh-0.1.6-alpha.1`），CI 会自动解析，无需改 Dockerfile；
- ⚠️ **不要**在任何文档里建议用户 `npm install -g @deepseek-ai/dsh@latest` 来"升级到 0.1.6"——那条路永远是 0.1.5-rc.1；同理，它**也不是**升级到 rc.2 的路子（那要显式写 `@next`）；
- 升级文档 `docs/zh-CN/03-升级与维护.md` 建议补一句：**alpha 版本必须写全 `@0.1.6-alpha.1`**。

#### 附带发现：两条构建路径的默认版本不一致（建议一并修）

| 路径 | 生效默认值 | 实际装到的版本 |
|---|---|---|
| `docker build`（不带 build-arg） | `Dockerfile` 的 `ARG DSH_VERSION=latest` | **0.1.5-rc.1** |
| `docker compose build` | `docker-compose.yml` 的 `${DSH_VERSION:-0.1.5-rc.2}` | **0.1.5-rc.2** |

**不传 `DSH_VERSION` 时，两条路径会产出不同 dsh 版本的镜像。** 这与 0.1.6 无关，是既有状态，但既然本轮要动版本号，建议一并统一：把 `Dockerfile` 的默认值也钉成显式版本号（而非 `latest`），或让二者跟随同一个来源。否则 `latest` 这个"浮动"默认值还会随 npm tag 变动而**静默漂移**到别的版本。

### P1 —— 探针失败文案补充（低成本、高收益）

`scripts/probe-ready.js`：

```js
const FAIL_BODY_PATTERNS = [
  /Failed to load plugins/i,
  /did not activate/i,
  /dsh-boot-(error|failed)/i,
  /required startup failure/i,   // ← 新增：0.1.6 的新文案
];
```

**理由**：0.1.6 区分了 optional（warn）与 required（fatal）两类失败。补上该模式后，L4 能同时覆盖两类。

> ⚠️ **同时注意一个语义变化**：0.1.6 中"可选插件失败但应用照常启动"时，stderr 会打印 `N entries did not activate` 警告。
> 而 L4 是**读 HTTP 正文**判断的（不是 stderr），所以**不会**因此误判——但前提是这类警告不出现在返回的 HTML 里。实测正常启动的 HTML 不含该文案，**当前不会误判**。
> 不过若未来 dsh 把警告渲染进页面，L4 会把"健康但不完美"判成不健康并触发自愈。建议保留 `RESCUE_PROBE_FAIL_CHECK=off` 逃生阀（已存在）。

### P2 —— 快照范围补全（防御性）

`scripts/librescue.sh` 的 `rescue_snapshot()` 目前抓：`package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`node_modules`。

**建议**：把 `.dsh-module-fallback` 一并纳入（它与 `node_modules` 通过 symlink 关联，缺失可能导致回滚后悬空链接）。

```sh
  for f in package.json pnpm-lock.yaml pnpm-workspace.yaml; do
    if [ -f "$pdir/$f" ]; then cp "$pdir/$f" "$RESCUE_DIR/$snap/$f"; fi
  done
  # 新增：模块回退目录（0.1.5+ 存在，与 node_modules 的 symlink 关联）
  if [ -d "$pdir/.dsh-module-fallback" ]; then
    cp -a "$pdir/.dsh-module-fallback" "$RESCUE_DIR/$snap/.dsh-module-fallback" 2>/dev/null \
      || rescue_log "snapshot: .dsh-module-fallback copy failed"
  fi
```

对应 `rescue_restore()` 也需同步还原，且 `snapshot_tree_hash` 的覆盖范围要一并考虑。

### P2 —— 文档：preset 名称核查

检查仓库文档与 `.env.example` 是否残留 preset 名 `code`（应为 `ptc`）。此为 0.1.5 的变更，但若从未同步，升级到 0.1.6 时会暴露。

### P3 —— CI 缓存注意

分支构建的 `DSH_VERSION=latest` 是固定字符串 —— 由于 `latest` 仍是 0.1.5-rc.1，**分支构建不可能产出 0.1.6 镜像**。这符合当前设计（分支构建不发布），但如果想验证 0.1.6，必须走 tag 构建或手动 `--build-arg DSH_VERSION=0.1.6-alpha.1`。

## 五、建议的发布流程

```bash
# 1. 本地验证（不发布）
docker build \
  --build-arg DSH_VERSION=0.1.6-alpha.1 \
  -t dsh-docker:test-0.1.6 .

# 2. 跑仓库自带的单测与 e2e
sh scripts/t/test-compose-wiring.sh
# ... 其余 scripts/t/test-*.sh

# 3. 确认容器内版本自证
docker run --rm --entrypoint /opt/dsh-seed/bin/dsh dsh-docker:test-0.1.6 --version
# 期望输出：0.1.6-alpha.1

# 4. 通过后打 tag 发布（CI 自动解析 DSH 版本并构建多架构镜像）
git tag v0.5.0-dsh-0.1.6-alpha.1 && git push origin v0.5.0-dsh-0.1.6-alpha.1
```

> CI 的镜像自证步骤（`/opt/dsh-seed/bin/dsh --version` 必须等于 tag 后缀）已能覆盖本版，无需改 workflow。

## 六、剩余不确定项（需真机 Docker 验证）

以下在本环境（无 Docker daemon）无法验证，建议在真实宿主机补测：

1. **多架构构建**：`node-addon-require-builtin@^0.1.6` 含原生 addon，`docker buildx` 的 arm64/amd64 交叉构建是否正常。
2. **`--allow-scripts`**：npm 10+ 对 `node-pty`、`koffi` 等含 install script 的包默认拦截。镜像构建日志显示 0.1.6 下这些包仍会 warn —— 需确认镜像内 `node-pty` / `koffi` 是否**真的完成了编译**（终端/PTC 功能依赖它们）。这是**本次最值得真机验证的一项**。
3. **冷启动耗时**：0.1.6 依赖树仍为 ~441 包，seed 复制耗时与 `RESCUE_START_TIMEOUT`（默认 120s）的余量。
