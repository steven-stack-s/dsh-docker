# 06 · 救援模式

> [English](../en/06-rescue-mode.md) | [简体中文](06-救援模式.md)

DSH Docker 的**插件救援模式**：插件更新/安装导致启动失败时，自动回退到最近一个能跑的插件树、服务自动恢复；极端情况下用干净的**救生舱（lifeboat）**提供可操作入口。所有用户数据（会话 / 配置 / 凭据 / 记忆库）全程保留。

> 详细设计见《[06 · 救援模式设计规范（内部文档）](06-救援模式-设计规范.md)》。

## 1. 设计目标

本仓库把 DSH 拆成两部分持久化：

- **主程序** /opt/dsh（npm 全局包，`npm install -g` 升级）
- **插件树** $DSH_HOME/profiles/web（cordis.patch.yml + package.json + pnpm-lock.yaml + node_modules，由 `dsh plugin` 管理）

**插件更新/安装是最高频的启动失败来源**。一旦 boot 失败，`restart: unless-stopped` 会无限 crashloop，容器起不来时手动命令根本没有机会执行。救援模式为此设三道防线：

| 层 | 作用 | 触发 |
|---|---|---|
| 第 0 层 · 封装命令 | `rescue plugin` 变更前自动快照当前插件树；`rescue dsh-upgrade` 记录 last-good 主程序版本 | 手动执行封装命令 |
| 第 1 层 · entrypoint 自动回退 | boot 失败自动回退到最近 known-good 快照并重试 | 默认开启（RESCUE_AUTO=on） |
| 第 2 层 · 救生舱 lifeboat | 回退预算用尽仍失败时，用干净最小 profile 起可操作入口 | RESCUE=1 手动 / 自动降级 |

## 2. 如何启用

救援能力默认**已开启**，无需额外配置：

1. 镜像需包含救援工具集（`/opt/dsh-rescue` 与 `rescue` 命令），由本仓库 Dockerfile 打包。若你的容器较旧、`docker exec dsh rescue status` 报 command not found，请重建容器：
```bash
docker compose up -d --build
```
2. 数据卷无需迁移——快照存于 DSH 数据卷内（见 §6）。

相关环境变量（`.env`；容器内可用 `docker exec dsh env | grep RESCUE` 查看）：

| 变量 | 默认 | 说明 |
|---|---|---|
| RESCUE | 0 | 0=正常；1=救生舱启动（见 §5） |
| RESCUE_AUTO | on | on=启动失败自动回退；off=关闭自动回退 |
| RESCUE_START_TIMEOUT | 120 | 启动就绪探测超时（秒） |
| RESCUE_KEEP | 3 | 保留的最近快照份数 |
| RESCUE_PROFILE | web | 回退 / 插件操作目标 profile |

## 3. 命令速查

在宿主机上用 `docker exec dsh rescue ...` 操作（容器内也可直接 `rescue ...`）：

| 命令 | 行为 |
|---|---|
| `docker exec dsh rescue status` | 查看快照列表、当前指针、DSH 版本、最后事件日志（只读） |
| `docker exec dsh rescue snapshot` | 手动为当前插件树拍快照（作为回退目标） |
| `docker exec dsh rescue doctor` | 只读诊断：profile 目录与 package.json、快照列表、evidence/state/incident 目录健康、上次运行状态 |
| `docker exec dsh rescue plugin add <包名>` | 先自动快照、再执行 `dsh plugin --profile web add <包名>`（装前先留回退点） |
| `docker exec dsh rescue plugin remove <包名>` | 同上，用于卸载插件 |
| `docker exec dsh rescue rollback` | 手动回退到最新快照（打印提示后需 `docker restart dsh`） |
| `docker exec dsh rescue dsh-upgrade <版本>` | 记录当前 DSH 版本为 last-good，再升级主程序到指定版本 |
| `docker exec dsh rescue dsh-reinstall` | 按记录的 last-good 版本容器内重装主程序（主程序事故时的轻量兜底） |
| `docker exec dsh rescue lifeboat` | 打印切换到救生舱的操作指引（等价 RESCUE=1） |
| `docker exec dsh rescue report` | 总览最近事故（incident）表：phase / 根因类别 / 肇事插件 / 自愈 outcome（见 §4b） |
| `docker exec dsh rescue report <id>` | 展开单条 incident 全字段（rationale / 自愈动作 / evidenceRef / redline 断言） |
| `docker exec dsh rescue report --json` | 输出 incidents 的合法 JSON（供脚本消费） |
| `docker exec dsh rescue incident list` | 列出已记录 incident 的 id |
| `docker exec dsh rescue snapshot --reason '<text>'` | 手动快照并带触发上下文（如 `--reason 'plugin add @scope/x'`），供后续归因 |

> 安装/卸载/回退插件后，用 `docker restart dsh` 让 entrypoint 以新插件树启动；若启动失败，entrypoint 会自动回退（见 §4）。

> 注：`dsh-upgrade` / `dsh-reinstall` 是 `rescue` 的子命令，完整命令为 `docker exec dsh rescue dsh-upgrade <版本>` 与 `docker exec dsh rescue dsh-reinstall`。

## 4. 自动回退机制（entrypoint）

重启时 entrypoint 以**子进程**方式启动 dsh web，并对容器内 127.0.0.1:3081 做就绪探测，最多等 `RESCUE_START_TIMEOUT`（默认 120s）。判定“起不来”= 窗口内 3081 未开始监听，或 dsh 主进程直接退出。

回退流程：

1. 启动失败 → 若 `RESCUE_AUTO=on` **且**存在快照 **且**剩余尝试次数 > 0；
2. 取最新快照，校验其指纹与当前 live 插件树不同（指纹 = package.json + pnpm-lock.yaml 的哈希）；
3. 不同则把插件树（package.json / pnpm-lock.yaml / pnpm-workspace.yaml / node_modules）回滚到该快照并**重试**启动（最多 `RESCUE_KEEP+1` 次）；
4. 回滚不可用 / 预算用尽仍失败 → 转入**救生舱**（§5），或退出交由 `restart: unless-stopped` 兜底。

boot 成功后 entrypoint 会持续等待 dsh；若此后 dsh 崩溃，容器退出，由 Docker 重启策略接管。回退是否发生可看日志：

```bash
docker logs dsh --tail 100 | grep -iE 'rollback|healthy|rescue'
```

**审计日志**。除了容器日志，所有救援事件也会追加写入数据卷内一个文件——**`$DSH_HOME/.rescue/log/rescue.log`**（宿主机默认 `./dsh/.rescue/log/rescue.log`），即使容器日志丢失也能离线审计救援历史。内容含手动 `snapshot` / `restore apply|done` / `prune`，以及 entrypoint 现在记录的事件：

```bash
tail -20 /data/dsh/.rescue/log/rescue.log      # 容器内执行
# 例如 2026-09-07T15:35:24+0800 restore done snap-0002
#      2026-09-07T17:12:00+0800 auto-rollback start -> snap-0001
#      2026-09-07T17:12:03+0800 auto-rollback done -> snap-0001
#      2026-09-07T17:12:10+0800 lifeboat enter: rollback FAILED
#      2026-09-07T17:13:00+0800 boot exhausted, no rollback available; exit for docker restart policy
```

`rescue status` 显示的“最后事件日志”即该文件尾部。

## 4b. 自动排查 · 根因归因 · 智能自愈（rescue-diagnose）

在「自动回退」之上，entrypoint 提供**证据驱动的归因 + 智能自愈闭环**：启动失败 / 运行期崩溃时把每轮 dsh 启动输出 tee 捕获到证据目录，按**确定性规则**（非 LLM）归因根因，按决策矩阵自动处置，并把每次事故写成可审计 incident，用 `rescue report` 人读呈现。全程**严守红线**：只动插件树四件套（package.json / pnpm-lock.yaml / pnpm-workspace.yaml / node_modules）与 `$DSH_HOME/.rescue` 下的状态/incident，**绝不自动改** `cordis.patch.yml`、会话 / 记忆 / 配置 / 凭据。

**触发路径**

1. **boot 失败**（探测超时 / 子进程早退）：捕获该轮证据 → 调 diagnose 归因（读证据 + 审计 + 快照 meta 的 trigger/reason）→ 按 `recommendedHeal` 处置：`remove-plugin`（先快照现场，再经 `dsh plugin remove` 摘肇事插件，只动四件套）/ `rollback`（回退到变更前基线快照）/ `report-only`（不自动改，写 incident 提示）→ 写 incident 后重试或退出。

> **边界（真机实测）**：`remove-plugin` 经 `dsh plugin remove` 只清 `package.json` 的 `dependencies`，**不清 `dsh.profile.bundles`**（bundles 是 profile 插件组合声明，非 pnpm 依赖）。因此它仅对「依赖型插件故障」有效；对 **bundles 条目型启动故障**（如坏 bundle 引用导致无法解析），`dsh plugin remove` 会因「project has no dependencies」失败——该自愈会如实记录 `action outcome=fail` 并降级为 `report-only`（红线不破）。这类故障的**可靠自愈是 `rollback`**（回退到变更前基线）。诊断矩阵：offender = 最近新增（依赖型）→ `remove-plugin`；bundles 组合故障 → 交 `rollback` 兜底。
2. **运行期崩溃**：dsh healthy 后异常退出 → 写 last-run（abnormalExit）并退出（沿用 docker restart 交接，不在 PID1 内无限拉起）；下次启动读到异常 → 记录 runtime incident，用 `rescue report` 复核。**保守默认：运行期崩溃仅自动报告归因，不自动摘/回退**（避免把无关崩溃误伤），由人工按报告处置。

**自愈护栏**（防无限 / 防误伤）：

- 自愈预算写 `state/selfheal.json`：单容器生命周期内自动摘插件 ≤ `RESCUE_REMOVE_LIMIT`、回快照 ≤ `RESCUE_ROLLBACK_LIMIT`，超限转 report-only。
- 归因保守（宁报告勿错拆）：仅当证据日志命中插件失败且肇事插件 = 最近一次新增时才 `remove-plugin`；其余优先回基线或只报告。
- 每次自愈动作前先快照现场；全部动作写 `rescue.log` + 更新对应 incident。
- `RESCUE_SELFHEAL=off` 时只诊断 + 写 incident + 提示，绝不自动改。

**证据与事故落盘**（都在数据卷 `$DSH_HOME/.rescue/` 下）：

- `evidence/boot-<seq>-<ts>/`：每轮启动的 dsh 输出（dsh.log）+ 临时件。
- `incidents/inc-<ts>-<rand>.json`：一次事故的归因 + 自愈动作 + redline 断言；保留 `RESCUE_INCIDENT_KEEP`（默认 20）份。
- `state/last-run.json`、`state/selfheal.json`：最近运行状态 / 自愈预算。

查看某次事故：`docker exec dsh rescue report <id>`；示例输出含 `rootCause.rationale`（为什么这么判）与 `redline.cordisPatchTouched=false`（本轮未触碰 cordis.patch.yml 的断言）。

> 真机校准提示：归因用的日志模式表在 `/opt/dsh-rescue/diagnose.js` 顶部 `PLUGIN_FAIL_PATTERNS`（可调数据常量）。若某类真实失败未被命中而误判 report-only，可在宿主上用 `docker exec dsh rescue report <id>` 回看 evidence 后手动调参一次。

## 5. 救生舱（lifeboat）

插件树坏到自动回退也救不回来时，用**干净最小 profile** 起一个不含第三方插件的 web（仅 DSH 核心），仍绑定同一 `$DSH_HOME`——用户数据原样可读、只是不加载坏插件，方便你删坏插件 / 改 cordis.patch.yml / 重装主程序。

进入救生舱：

```bash
# 编辑 .env：把 RESCUE 设为 1，再重建容器
RESCUE=1
docker compose up -d
```

救生舱启动后仍通过外部 3080 访问（容器内 socat 把 3080 转发到 3081 的 lifeboat）。此时可用 `docker exec dsh` 执行维护命令（删坏插件、改配置）。

退出救生舱恢复正常：

```bash
# 编辑 .env：把 RESCUE 设回 0，再重建容器
RESCUE=0
docker compose up -d
```

> 救生舱硬约束：绝不改动现有 `profiles/web/` 与任何用户数据文件；lifeboat 自身产生的会话/记忆独立存于 `profiles/lifeboat` 名下，可事后清理。

## 6. 关闭方法 / 备份提示

**关闭自动回退**：把 `.env` 的 `RESCUE_AUTO` 设为 `off` 后 `docker compose up -d`。关闭后启动失败不会自动回退，而是退出交由 `restart: unless-stopped` 反复重试，建议保留默认开启。

**完全停用救援模式**：封装命令本身是手动工具无法关闭；把 `RESCUE_AUTO=off` 与 `RESCUE=0` 即回到“不自动干预”的普通部署。

**备份提示**：救援快照位于 DSH 数据卷内 `$DSH_HOME/.rescue`（宿主机默认 `./dsh/.rescue`），随 `dsh/` 一起被备份——按《[03 · 升级与维护](03-升级与维护.md) §5 备份》备份整个部署目录即可，无需单独处理。快照与回退**只动插件四件套**，永不触碰会话 / 记忆 / 配置 / 凭据。

## 7. 故障排查入口

- 容器起不来 / 反复 crashloop → 先看 `docker logs dsh --tail 100` 是否有 `rolling back` / `lifeboat` 标记，再结合《[04 · 故障排查](04-故障排查.md)》定位。
- 需在真实 Docker 宿主机端到端验收救援链路 → 运行仓库内脚本 `scripts/t/e2e-rescue-on-host.sh`（会短暂重启 dsh 容器，见脚本头注释）。
